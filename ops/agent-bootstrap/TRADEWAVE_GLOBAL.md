# TradeWave global agent bootstrap

Apply these rules only when the repository remote or workspace identifies TradeWave TW2.

1. Before planning or editing, fetch current `origin/main` using the repository's required Git user.
2. Read `AGENTS.md`, `CLAUDE.md`, `docs/RELEASE_PROCESS.md`, `.claude/skills/tw-git-release-workflow/SKILL.md`, and `.claude/skills/tradewave-deployment-manager/SKILL.md` from current `origin/main`. If an old worktree lacks them, use `git show origin/main:<path>`; do not declare them missing until the current remote ref is checked.
3. Start each task in a separate clean branch/worktree based on current `origin/main`. Never develop in the operational `/home/flask` checkout or an unrelated dirty worktree.
4. A substantive application/runtime change is complete only when it is committed, pushed, running on dev, and verified there. Use the fast dev loop by default: focused affected-surface tests, one affected build when required, a short activation lock, and one live smoke. Do not run staging's manifest, full regression, target audit, snapshots, or broad account-tier/browser gates during routine dev completion. Exceptions require an explicit `local only` or `do not deploy` instruction, or an analysis/documentation-only request.
5. Claude and Codex may develop concurrently in separate worktrees. Serialize only the brief final dev activation: acquire the lock after testing/building, refetch `origin/main`, preserve completed changes, activate, live-smoke the affected behavior, advance main without force, prove application parity, and release the lock. If main moved, integrate it and rerun only affected checks/builds.
6. "Staging-ready" means clean, pushed, live on dev, and focused-tested. It does not mean staging qualification has run. Non-runtime documentation/policy-only commits may advance main without rebuilding dev when the application tree is unchanged.
7. Branches, commits, pushes, worktrees, handoffs, locks, builds, and routine conflict resolution are agent responsibilities. Do not ask Afshin to manage them, and do not say fixed/done/live while application work exists only in a private worktree.
8. `Deploy to staging` authorizes the full gated release workflow for the current live dev behavior: release ID and manifest, full regression, immutable artifact proof, target-drift audit, required contract/browser/account-tier checks, staging writes, verification, and automatic rollback. Production always requires a later explicit request and its snapshot gate.
