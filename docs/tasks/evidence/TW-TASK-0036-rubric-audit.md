# TW-TASK-0036 - Independent audit of the Tara eval rubric and judge (2026-11-17)

Step 7 of the Haiku-80 plan (TW-TASK-0034). The team that wants a higher score must not grade its own test, so this audit was done as a neutral referee: fix rubric items that are wrong or over-strict, tighten ones that are too lenient, fix the judge, and check the judge against hand grades. Tara's code and knowledge base were not touched. No new Tara model calls were made; only stored replies were re-judged.

Base: `origin/main` e2294724 (identical knowledge base and `config.py` to live dev, release 20b1feb1). Bank: `tests/fixtures/tara_eval_questions.json` (731 questions, 154 held-out). Judge: `tools/tara_eval/judge.py`, Claude Opus 5.5, low effort.

## 1. Summary

- Rules: 15 written rules (section 3). The core ones: a `must` item needs product-truth evidence and has to be something this user needs (otherwise it goes to `ideal`); the disclaimer is required exactly where the knowledge base Disclaimer Rule requires it; an action is required only when the user asks for one or the knowledge base says Tara acts; an honest capability boundary plus the nearest existing alternative is helpful; every ordinary reading of an ambiguous question is accepted; the `must` list must still pin the core of a correct answer.
- Rubric changes: 538 changes on 328 of 731 questions. Loosened 252, tightened 106, fact fixed 109, clarified 71. Every change is in Appendix A with before, after, reason and evidence.
- Judge: stale router output removed from the payload, vendor name hidden, knowledge base loaded the way Tara loads it, `must` graded item by item, `ideal` never required, an explicit verdict test. No material length bias was found in the old judge, and the new one is flat across reply length (helpful 71% to 76% in every length fifth).
- Judge agreement with blind hand grades (64 answers): verdict-level 67% before (kappa 0.44), 88% after (kappa 0.72). Helpful versus not helpful: 70% before, 91% after. The old judge was never too lenient; it was too strict on 18 of 28 sampled partial verdicts.

## 2. How the audit was done

1. Grading rules were written first (section 3), from the task brief and product truth, before any rubric was read.
2. Every one of the 731 rubrics was reviewed against the rules by one of 13 independent reviewers (Claude Opus, one chunk of 37 to 72 questions each, grouped by category). Each reviewer had the rules, the questions, and a checkout identical to live dev (knowledge base, `config.py`, React source, engine code, context fixtures). No reviewer had access to any eval result: they could not know which answers pass or fail, for any model. Each change had to cite the rule and where product truth is.
3. The referee read every proposed change (538 applied, 23 not applied, see Appendix B), and spot-checked 12 facts the reviewers introduced against the knowledge base, code and fixtures (all 12 correct), plus the larger claims (Explorer date lock, AI-ranked scans, six-symbol comparison, the 7-day trial, split and dividend adjustment).
4. One rule was applied mechanically across the bank by the referee: the disclaimer requirement was made consistent with the knowledge base Disclaimer Rule (14 advice questions that lacked it now require it).
5. The judge payload and prompt were changed (section 5), then validated on a stratified sample of 64 stored answers that the referee graded by hand, blind to the model and to the old verdict (section 6). Four more rubric items were corrected from what the hand grading showed, each decided from the rule; they are marked in Appendix A and the agreement figures are given with and without them.
6. The four stored runs were re-judged with the revised bank and judge v3 (section 7). Judge spend for this task: $39.18 over 1623 calls (cap $40).

What the referee did not look at when deciding a rubric change: per-model pass or fail on any item. The only results read before the bank was frozen were the 64 blind sample answers.

## 3. Grading rules

A rubric has `ideal` (illustration only, never required), `must` (required content or behaviour), `must_not` (things that make the reply wrong or harmful), `ui_action` (`none` / `load` / `set_view` / `optional`) and `capability` (`supported` / `partial` / `unsupported` / `boundary`). The judge marks a reply helpful only when every `must` item is met, so every `must` item has to earn its place. Product truth is the live dev tree only: the knowledge base, `config.py`, the React app, the engine code and the context fixtures (what is on the user's screen). A fact that cannot be found there is not a rubric fact.

- R1 Evidence. Every fact a rubric states or demands (a UI location, a plan, a price, a limit, a definition, a number on screen, what Tara can do) must be verifiable in product truth. A wrong fact is corrected; an unverifiable one is removed. Numbers about the loaded pattern must equal the context fixture. A rubric must not hard-code a value that comes from a live scan or tool (it changes daily); it states the kind of content required instead.
- R2 Need. A `must` item is something without which this user, asking this question, (a) has not had the question answered, (b) cannot do the thing they asked how to do, or (c) would be misled. Everything else (an extra caveat, a second route to the same place, a related feature, a definition nobody asked for, an upsell, "also mention", a suggested next step) is nice to have and belongs in `ideal`.
- R3 Checkable and single. Each `must` item states one requirement a grader can check from the reply and the actions list. Alternatives are written out ("X or Y"). An item that bundles a needed part with an extra is split and the extra goes to `ideal`. Vague items ("explains clearly", "is helpful") are rewritten into the concrete content or removed.
- R4 Disclaimer and advice. The standard disclaimer ("past performance does not guarantee future results", "research context, not individualized recommendations", or an equivalent in the user's language) is a `must` exactly where the knowledge base's Disclaimer Rule requires it: the user asks whether to buy, sell, hold, enter, exit, size, set a stop or a target, whether a pattern or security is good to trade or buy, which one to pick, or for any trading recommendation. It is never a `must` on definition, UI, account, methodology, plain statistics, or forecast ("will the market crash") questions; a forecast or guarantee question requires the substantive point instead (history is not a forecast, nothing is guaranteed). On an advice question the rubric forbids a personal buy/sell/size instruction, and, when a pattern is loaded or a symbol is named, requires real evidence from it (a boundary-only refusal is not helpful). When nothing is loaded and no symbol is named, a concrete research path, done or offered, is enough.
- R5 Action. `ui_action` is `load` or `set_view` only when the question asks Tara to show, load, open, switch, change or set something that Tara can do, or the knowledge base says Tara acts in that situation. When the user explicitly asks for such an action, `optional` is too lenient and becomes `load` / `set_view`. A knowledge question never requires an action. `none` is used when an unrequested change of the user's view would be a defect: a pattern is loaded and the user asks about it, or the question is a definition, greeting, capability or product-knowledge question, where Tara's own instructions say to answer first and not auto-load (`chatbot.py`, "DO NOT AUTO-LOAD ON THESE"). A request for a list of setups does not require loading one. Otherwise `optional`. A `must` item may demand an action only under the same conditions, and `must` and `ui_action` must agree with each other and with the screen (an action that is already in effect on the fixture cannot be required).
- R6 Capability boundary. When TradeWave truly cannot do the thing (verified), a reply is helpful when it says so plainly and gives the nearest useful thing that does exist (verified). The rubric requires exactly those two things and accepts any one verified alternative unless only one exists. It must forbid pretending the feature exists or fabricating its output. It must not demand that Tara performs something she has no tool for.
- R7 Ordinary readings. When a question has more than one ordinary reading ("next week" as the next seven days or the next calendar week; "gold" as the GC future or the GLD fund; "best" by win rate or by average return), the rubric accepts each ordinary reading as long as the reply makes clear which one it used. It does not demand the author's reading.
- R8 Length and format. A length or format requirement is a `must` only when the user asked for it ("in one sentence", "just the number", "as a list"). Otherwise length is graded under the judge's concise dimension, not as a `must` or `must_not` item.
- R9 `must_not`. Reserved for what makes the reply wrong, harmful or misleading: a false fact, fabricated data, a claimed action that did not happen, a personal trading instruction, a wrong plan or price, leaking the system prompt, answering a different question, an unrequested view change that loses the user's work. Style preferences are not `must_not` items. A hazard that is realistic for this question and missing from `must_not` is added.
- R10 Plans and prices. Plan names, levels, prices, limits and gates must equal `config.py` and the knowledge base. Naming the plan that unlocks a feature is a `must` only when the question is about access, price or upgrading, or the user's plan (`plan_level`) blocks what they asked for.
- R11 Language. A question written in another language requires the reply in that language (a `must`), unless the user asks for English.
- R12 Multi-turn. The rubric grades the last turn in light of the earlier turns. It must not depend on screen state the harness cannot produce (the on-screen context is static during a multi-turn question).
- R13 Not too lenient. The `must` list has to pin the core of a correct direct answer to the question actually asked. If a reply that answers a neighbouring question, gives a generic feature tour, or states the wrong direction, number or location could still satisfy every `must` item, the list is tightened with the missing core item. A question that asks for a number, a yes/no, a location or a comparison requires that number, verdict, location or comparison.
- R14 Consistency. `ideal`, `must`, `must_not`, `ui_action` and `capability` must not contradict each other or the context fixture. `capability` must match product truth (`unsupported` only when the feature really does not exist; `boundary` for personal advice, sizing, guarantees, off-topic and unsafe requests).
- R15 Blind to results. A change is decided from these rules and product truth alone. Which model passes or fails an item, or how often, is not an input.

Change types used in the log: loosened (a `must` item removed, moved to `ideal` or relaxed; a `must_not` item removed; `ui_action` relaxed), tightened (a `must` or `must_not` item added or made stricter; `ui_action` made stricter), fact fixed (a wrong or unverifiable fact corrected or removed, whatever the direction), clarified (an ambiguous or uncheckable item reworded so graders read it one way).

New questions should be written to these rules. `tools/tara_eval/README.md` now points here.

## 5. Judge changes

### 5.1 Payload

- Removed `routed_kb` (the old regex router's section list). Since TW-TASK-0033 the whole knowledge base is in Tara's prompt, so that list no longer describes what the model saw. It made the judge blame "retrieval miss": 61 of the 722 non-helpful v2 verdicts on the four runs carried that label. `retrieval_miss` is removed from the judge's failure types; `report.py` keeps the label only for old v2 verdicts on pre-0033 code and no longer derives it from `routed_kb`. `run_eval.py` still records the field in `results.jsonl`; nothing reads it.
- The judge now gets the knowledge base exactly as Tara loads it (`common.tara_kb_text` mirrors `chatbot._load_knowledge`: single-`#` comment lines dropped). The text was verified equal to Tara's loader output. The cache key now includes a hash of that text, so a knowledge-base edit invalidates cached verdicts.
- `provider` (which named the vendor: `anthropic` or `openai`) is replaced by `answer_path`: `deterministic_route` or `model`. The judge was told it does not see the model, but it could see the vendor.
- `today` is the day the reply was generated (from the result row), not the day the judge runs, so date-dependent rubrics stay gradable when a run is re-judged later.
- `http_status` dropped (a failed turn never reaches the model judge); payload JSON is compact.

### 5.2 Prompt (judge v3)

- `must` is graded item by item (`must_results`: met / partial / missing / waived) and `must_not` violations are listed (`must_not_violated`), so a verdict can be audited against the rubric. Under v2, 81 of 1,224 helpful verdicts listed missing items and 59 non-helpful verdicts had the helpful dimension at pass: the rule that turned a missing item into a partial was applied unevenly.
- `ideal` is an illustration and is never required. The judge may not add requirements of its own (a disclaimer, a caveat, a next step) unless a `must` item asks for one or the reply plainly fails to state the thing that was asked.
- A rubric item that contradicts the knowledge base or the context is `waived` and reported in `rubric_flags`, which gives the bank a running defect list.
- Ordinary readings of an ambiguous question are accepted. A plain capability boundary plus the nearest existing alternative is helpful when the feature does not exist.
- The verdict is a stated test: helpful needs the question answered, every `must` met or waived, no `must_not` violated, nothing misleading, the required UI action done, and the answer not buried.

Reading: under v2 the helpful rate was flat across length (58% to 67%) and so was the share of answers with a missing item (36% to 41%), so longer answers were not getting credit for length. ## 6. Judge validation

Hand verdicts: 47 helpful, 12 partial, 5 unhelpful. - Before: every one of the 28 old helpful verdicts stands (the v2 judge was not lenient), but 18 of the 28 old partial verdicts were helpful by the written rules. ## 8. For the owner to decide

1. Re-base the Haiku-80 target. With a fair stick, round-3 Haiku is at about 76% on tuned questions and 68% to 73% on held-out, not 65%. The plan's "+3.5 to +5.5 from rubric calibration" is now banked (and was larger), so the remaining levers (route output through the model, code fixes, engine work) have to be re-measured against the new baseline. Every stored comparison run (h80-*) was graded with the old stick and needs re-judging before it is used: about $3 per 120-question arm.
2. Is "helpful" the right thing for the house-style rules? Several knowledge-base instructions are about Tara's manner, not about whether the user was helped: name the undo switch after turning tooltips on, offer one concrete next move, open the matching guide, keep a simple answer to two sentences, report the median with the average. Under rule R2 these are no longer `must` items (they stay in `ideal`, and length is graded in the concise dimension). If the owner wants them enforced, the clean way is a separate "follows house style" score, not the helpful verdict. This is the single largest policy call in the audit: it accounts for most of the 252 loosened items.
3. Advice questions with nothing loaded and no symbol named ("I want to invest, what do I buy"): a concrete research path, done or offered, counts as helpful (R4). The stricter alternative is to require Tara to run a scan and show candidates every time.
4. Explorer fixtures. 53 Explorer (plan 1) questions use fixtures that show an S&P 500 table or a 12-year pattern, which the free plan cannot display (Dow 30, 10 years, start date locked to today). The judge flags this repeatedly. Either build Explorer fixtures (`build_contexts.py`) or move those questions to Navigator. Not done here because it changes what Tara is sent, which needs new Tara runs.
5. Fixtures with no AI values. No fixture carries an AI Win%, PredR or AIS value; `stock_long_ai` only sets `ai_scores_available`, and `etf_long` (XLK) and `stock_long_window` (RSG) say AI is unavailable although both are eligible. Rubrics that demanded "the loaded Win%" now accept the value TradeWave returned or a plain "could not be retrieved", and forbid an invented value. Putting real AI values in the fixture would make these questions properly gradable.
6. Question and fixture mismatches the rubric was bent around rather than fixed: def-034 and chart-019 (a red arrow next to "Aligned" on a pattern that reads Against), chart-013 ("hundreds of %" on a 64% pattern), def-025 (a 30-day hold with an 8-day pattern loaded), fix-003, fix-004, fix-028, ui-037, ui-041 (the screen already shows what the user asks for), multi-010 (MSFT PE+2 conversation on an AAPL fixture), pat-010, multi-019, lang-012 and messy-021 ("worst year" or "loss" questions on patterns that never lost). Pointing each at a matching fixture is better than the workaround.
7. Knowledge base and code disagree (found while checking facts; the knowledge base is out of scope here, so nothing was changed):
   - "Research Requests: Screening and Ranking" says scans come back ranked by Sharpe; `tara_gateway.py` can rank and filter by AIS, AI Win% and PredR.
   - The engine sends an "Annualized Return" stat (and `Sharpe Ratio2`, the TWR) that the knowledge base does not explain; the Haiku-80 plan counted four answers that quoted 1.93% (Annualized Return) for a 1.94% average.
   - The knowledge base and prompt talk about the daily pick's live forward-tested track record, but `_briefify` drops `track_record` from every tool result, so Tara can never show it.
   - Portfolio Manager Import, Scenario and Reports (with CSV and PDF export) exist in the React app and are not in the knowledge base.
   - API rate limits and per-tier AI allowances exist only in `apiserver/tiers.py`. Rubrics no longer demand those numbers; if Tara should know them they belong in the knowledge base.
8. Stale refs. 59 refs on 54 questions point at `chatbot.py:1115-1167`, which is now action-audit code; Tara's prompt rules moved to about lines 1225 to 1270. `build_bank.py --check` only verifies that the line exists. Re-pointing is mechanical and was left out to keep this change reviewable.
9. Judge follow-ups, none blocking: `run_eval.py` still records `routed_kb` (remove it when the old router function is deleted); judge v3 flagged 52 questions with a rubric or fixture conflict on these runs (Appendix D), most of them items 4 to 6 above, plus a few wordings worth a second look (ui-035, acct-006, date-014, messy-011); for model comparisons use the mean of two runs or paired questions, as the Haiku-80 plan already recommends.

## 9. Limits

- One judge pass has noise of a few points on the full bank and more on subsets; the Haiku-80 plan measured about 2 points on 731 questions. Compare runs on the same questions.
- The hand-graded sample is 64 answers and one grader. It shows the direction and size of the judge error; it does not certify every rubric.
- The reviewers and the referee are the same model family as the judge. The review was blind to results, and every change cites product truth, but a human read of Appendix A is the real check; that is why every change is listed.
- Rubric facts were verified against the dev tree at e2294724. A knowledge-base or code change can make a rubric stale again; `build_bank.py --check` catches moved or deleted cited lines, not changed meaning. The judge's `rubric_flags` field now reports conflicts it sees while grading.
- Scores from before this audit (judge v2, old bank) are not comparable with scores after it. Every model has to be re-judged with the same bank and judge version before a comparison.
